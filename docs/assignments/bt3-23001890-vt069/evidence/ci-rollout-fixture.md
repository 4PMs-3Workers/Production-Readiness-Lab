# CI rollout fixture regression

- Pull request: #66, initial failing head `222a8ae39a0b5f99d98191bcb7caa5004fffde42`.
- Remote job: `Serialized deployment and verified rollback`, step `Required isolated Linux rollback and committed-data proof`. Two duplicate workflow runs reported the same failure. The job log showed `tests/rollout/test_configuration_transition.py::test_reviewed_configuration_upgrade_and_rollback_preserve_the_existing_host`, at `RolloutStack.start()`, `AcceptanceFailure: Fixture schema failed`; each run reported 1 failed, 3 passed. This was after the container fixture schema command, before the old host was started.
- First root cause: `Artifacts.manifest(..., root=base)` built a release manifest for an archived predecessor tree, but assigned module-global current `SCHEMA` (`20261113_1200_booking_quota`). The predecessor release source declares `20261019_1200_proposal_replay`, so its schema service rejected the fixture contract.
- First test/fix: `test_manifest_uses_schema_revision_from_selected_source_tree` caught the mismatched revision; commit `6b1de05` changed manifest construction to read the pin from the selected source tree. The focused group passed 78 tests.
- Second CI failure on head `2a486313c276335567d0a55646b8cc9a96961427`: the old host proceeded further, then `render(manifest, root=base)` called `require_compatible`, which still compared against module-global current `SCHEMA` and raised `ReleaseError("incompatible-schema")`. The same rollback test failed at `RolloutStack(..., root=base)` while rendering the predecessor manifest. This confirms the first fix removed the startup schema failure but the manifest renderer still had a separate global-schema assumption.
- Extended RED: the same regression test now invokes `render(manifest, root=legacy_root)` and asserts the emitted `ACCEPTED_SCHEMA_REVISIONS` uses the predecessor value. It failed at `require_compatible` with `incompatible-schema`, not at setup/import.
- Follow-up fix: centralize reading the exact `SCHEMA` assignment from the selected tree in `tools/deploy/release_manifest.py`; use it both in `require_compatible` and the renderer's emitted schema environment. `Artifacts.manifest()` uses the shared helper. Targeted release/rollout group: 78 passed in 4.58s, exit 0; Ruff/Black/Pyright pass (408 files unchanged, 0 type errors).
- Limitation: the remote serialized rollback test exercises Linux/Docker not available locally. A new remote CI rerun is required; neither prior CI failure is called resolved until that rerun passes.

## Third CI finding: reviewed schema migration and rollback

- PR head `43e9942936f3f17446747205e4e8f24c542ea4a4` failed the same serialized Linux acceptance at the initial predecessor deployment. The state recorded `schema-incompatible` before the old host could reach `succeeded` (1 failed, 3 passed, 305.23 seconds in the push run; the PR duplicate reported the same failure in 309 seconds).
- Root cause: `rollout_schema.require_schema()` compared every database revision to the current module `SCHEMA`. The fixture was deploying the actual reviewed predecessor source whose revision is `20261019_1200_proposal_replay`; its schema also lacks the new `service_settings.max_active_appointments` column (confirmed in `git show 724169a33b852a6cc6b255aff7cb92fffed89908:src/backend/app/models/service_setting.py`).
- A first regression test, `test_predecessor_source_can_verify_its_selected_schema_revision`, failed at the current-schema-only guard. The next failure-path review showed the full rollout also needs to validate the previous stable manifest's revision before migration and permit that explicitly reviewed predecessor release to run against the additive current schema during rollback.
- Implemented a bounded compatibility rule: only the current schema and the repository-reviewed predecessor revision are recognized; current revision requires an exact current catalog; predecessor revision accepts only a subset of known current tables/columns; rollback of that predecessor may use the exact current catalog. The release consumer enables predecessor compatibility only for an explicitly expected prior selection. Upgrade preflight validates the prior stable's schema pin before migration, then the existing post-migration checks require the current pin.
- Tests: `test_predecessor_release_can_run_on_the_forward_migrated_current_schema` reproduced the rollback gate before the final change; `test_reviewed_predecessor_schema_requires_rollback_opt_in` guards the manifest opt-in; `test_upgrade_preflight_uses_the_previous_stable_schema_before_migration` verifies the exact prior manifest pin. Focused suite is 89 passed, exit 0; full backend suite on source `4a3b007` is 1,799 passed, 646 skipped, 1 warning, exit 0. Linux/Docker CI remains the definitive test of this path; the new run on `4a3b007` is still in progress.
