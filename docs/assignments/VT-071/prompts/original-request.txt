## V. HƯỚNG DẪN THỰC HIỆN THEO 5 PHẦN BÀI TẬP

### PHẦN 1. SPECIFICATION VÀ AI-ASSISTED PLAN

#### 1.1. Kiểm tra repository

Trước khi thiết kế feature, hãy:

- Truy cập repository chính thức.
- Xác định default branch và baseline commit SHA.
- Ghi nhận ngày kiểm tra.
- Đọc README, cấu trúc project, tài liệu API và instructions liên quan.
- Xác định framework, backend, authentication, authorization và database.
- Tìm những endpoint hoặc feature hiện tại có liên quan tới việc xuất dữ liệu.
- Tìm luồng đọc dữ liệu, kiểm tra quyền và các cơ chế idempotency/concurrency guard hiện có.
- Kiểm tra test framework và lệnh chạy test.
- Xác định integration boundaries giữa backend, database hoặc dịch vụ ngoài.

Không giả định hệ thống có những công nghệ hay module chưa được kiểm chứng.

#### 1.2. Problem statement

Viết một problem statement cho change request:

**Thêm endpoint/API xuất dữ liệu; chỉ người có quyền mới tải được và dữ liệu phải đúng phạm vi.**

Problem statement cần thể hiện vấn đề, người dùng liên quan và hậu quả nếu quyền truy cập hoặc phạm vi dữ liệu không được kiểm soát.

Không chốt sẵn công nghệ hoặc framework trong problem statement.

#### 1.3. Acceptance criteria

Viết từ 3 đến 5 acceptance criteria với các đặc điểm:

- Có mã AC-01, AC-02, ...
- Dùng Given/When/Then.
- Mô tả hành vi quan sát được.
- Có thể kiểm thử tự động.
- Bao quát truy cập hợp lệ, truy cập trái phép, giới hạn phạm vi và một failure path quan trọng.
- Không gắn một cách vô lý vào implementation details.

Lựa chọn trạng thái, quyền hạn, loại dữ liệu và format export dựa trên repository hoặc đánh dấu assumption.

#### 1.4. Non-functional constraints và invariant

Xác định ít nhất 2 non-functional constraints liên quan đến Security, Performance, Reliability hoặc data integrity.

Phải sử dụng đúng:

- 80 concurrent users/tasks.
- Mục tiêu p95 ≤ 2.5 giây.

Chỉ rõ invariant/contract quan trọng nhất. Ưu tiên invariant về người dùng chỉ có thể xuất dữ liệu trong phạm vi được phép, nếu phù hợp với domain thực tế.

Cần xác định vị trí kiểm tra invariant ở backend/database hoặc boundary phù hợp, không phụ thuộc riêng vào UI.

#### 1.5. AI-generated implementation plan

Trước khi viết code, dùng AI/coding agent tạo một implementation plan.

Lưu lại:

- Prompt thực tế.
- Assumptions.
- Files dự định sửa/tạo.
- API contract dự kiến.
- Test strategy sơ bộ.
- Những rủi ro hoặc dependencies có thể ảnh hưởng.

Sau đó đọc source code và **sửa hoặc bác bỏ ít nhất 2 điểm trong AI plan bằng evidence từ repository thật**.

Không tự tạo lỗi cho AI sau khi đã viết bài; phải giữ được bản plan ban đầu và phần review.

### PHẦN 2. RISK-BASED TEST STRATEGY

#### 2.1. Phân tích risks

Ưu tiên risk riêng của VT-071:

**Mock che giấu contract sai với database hoặc dịch vụ ngoài.**

Phải phân tích tại sao một unit test sử dụng mock có thể pass trong khi application tương tác sai với schema, query, response format, authorization context hoặc contract thật.

Nêu rõ boundary nào cần integration/API test sử dụng dependency thực trong test environment.

#### 2.2. Test portfolio

Lập strategy có:

- Unit tests cho logic cục bộ.
- Integration tests cho database hoặc service boundary.
- API tests cho authentication, authorization và response contract.
- E2E tests cho critical user journey nếu phù hợp.

Nêu rõ test nào chưa cần thiết hoặc không đem lại đủ giá trị trong phạm vi vertical slice này, kèm lý do.

Không mặc định càng nhiều E2E tests càng tốt.

#### 2.3. Bảng test cases

Tạo tối thiểu 10 test cases, đầy đủ:

| Test ID | Risk/Requirement | Test level | Precondition/Input | Expected result | Priority |
|---|---|---|---|---|---|

Test cases cần:

- Liên kết với acceptance criteria.
- Có mức ưu tiên rõ ràng.
- Có ít nhất 2 negative tests.
- Có ít nhất 1 failure-path test gắn với mock/real contract mismatch.
- Có các điều kiện về role, scope và access control.
- Có trường hợp liên quan tới boundary với database hoặc external service.
- Phù hợp với feature thật và môi trường hiện có.

#### 2.4. Decision table – bắt buộc

Phải thiết kế một **decision table thực sự**, không chỉ liệt kê test cases rồi gọi đó là decision table.

Bảng cần chứa:

- Conditions.
- Các giá trị điều kiện.
- Rules hoặc các tổ hợp điều kiện.
- Actions/Expected outcomes.
- Test case ID tương ứng.

Chọn điều kiện từ yêu cầu thực tế, ví dụ trạng thái authentication, authorization, data scope và input validity nếu phù hợp.

Giải thích vì sao chọn những combinations đó và vì sao có thể bỏ bớt combinations không hợp lệ hoặc ít rủi ro.

Test data phải nhất quán với decision table, không được tạo expected result thiếu căn cứ.

### PHẦN 3. TEST-FIRST AI-ASSISTED IMPLEMENTATION

#### 3.1. Vertical slice

Chọn một vertical slice nhỏ nhưng thực thi được, đại diện cho change request.

Không triển khai cả một hệ thống export lớn nếu chỉ cần một slice có thể chứng minh requirement trọng tâm.

Vertical slice phải đủ để kiểm tra một behavior quan trọng thông qua API hoặc executable harness.

#### 3.2. Baseline và branch

- Lấy commit SHA thực tế làm baseline.
- Tạo branch Git riêng theo tên phù hợp với VT-071.
- Ghi nhận branch và baseline.
- Không làm thay đổi branch chính của nhóm.

#### 3.3. Test-first / Red phase

Trước khi sửa implementation:

- Viết hoặc sinh test từ acceptance criteria.
- Chạy test thật.
- Kiểm tra test thất bại vì thiếu/sai behavior cần triển khai.
- Không chấp nhận test thất bại do syntax error, missing dependency hoặc setup sai làm bằng chứng red phase hợp lệ.
- Lưu command, log, file và commit liên quan nếu có.

#### 3.4. AI patch / Green phase

- Dùng AI hỗ trợ tạo một patch nhỏ.
- Giữ lại prompt và phần output thực tế.
- Review diff theo Scope, Design, Correctness và Evidence.
- Kiểm tra security, data scope và API contract.
- Chạy lại test.
- Lưu evidence pass/fail thực tế.
- Không chấp nhận AI tự tuyên bố patch đã đúng khi chưa có test execution.

#### 3.5. AI review sau khi chạy test

Đây là ràng buộc AI riêng của VT-071:

**Phải cho AI review patch sau khi chạy test.**

Thực hiện theo thứ tự:

1. Chạy test.
2. Cung cấp patch/diff và kết quả test cho AI review.
3. Ghi lại nhận xét thực tế của AI.
4. Xác định ít nhất một nhận xét đúng, có bằng chứng từ code/test.
5. Xác định ít nhất một nhận xét chưa đủ evidence.
6. Giải thích vì sao chấp nhận hoặc không chấp nhận từng nhận xét.

Không thay bước này bằng review plan trước khi code.

#### 3.6. Phương án fallback

Nếu repository chưa đủ điều kiện triển khai endpoint/API export:

- Chọn module gần nhất có thật.
- Tạo executable test harness hoặc characterization test.
- Sử dụng code thật hoặc hợp đồng phù hợp.
- Giải thích điều gì đã được kiểm chứng.
- Chỉ rõ những hành vi chưa thể kết luận đối với hệ thống thực tế.

Không viết rằng đã hoàn thành endpoint production nếu chỉ mới kiểm chứng bằng harness.

### PHẦN 4. WHO TESTS THE TESTS?

#### 4.1. Mutation / deliberate bug

Thực hiện mutation bắt buộc:

**Bỏ idempotency/concurrency guard.**

Mutation cần áp dụng vào code hoặc harness phù hợp với behavior cần bảo vệ.

Nếu endpoint export là thao tác đọc thuần túy và không có idempotency/concurrency guard tương ứng, không được tự tạo một guard giả rồi báo cáo như đang tồn tại. Hãy xác định cơ chế tạo export job, xử lý task, duplicate requests hoặc module/harness gần nhất có thể kiểm thử mutation và giải thích giới hạn.

Quy trình thực hiện:

1. Xác nhận baseline test pass.
2. Tạo mutation trong nhánh/commit tạm thời.
3. Chạy test trên phiên bản mutated.
4. Ghi lại test nào phát hiện mutation.
5. Nếu mutation sống sót, bổ sung/sửa test.
6. Chạy lại để kiểm tra khả năng phát hiện.
7. Khôi phục implementation đúng.
8. Xác nhận nhánh nộp bài không chứa deliberate bug.

#### 4.2. Coverage

Nếu công cụ hỗ trợ, thu thập:

- Line coverage.
- Branch coverage.

Đồng thời phân tích risk coverage theo acceptance criteria.

Giải thích rõ:

- Những behavior đã được kiểm thử.
- Những behavior chưa có bằng chứng.
- Những điều coverage cao không chứng minh được.
- Mức confidence thực tế sau khi kiểm thử.

Không lấy 100% coverage làm bằng chứng software hoàn toàn đúng.

#### 4.3. Flaky-test review

Kiểm tra ít nhất 2 nguy cơ flaky test từ:

- Time.
- Test order/shared state.
- Network.
- Concurrency.
- Random test data.

Với mỗi nguy cơ, ghi:

- Nguyên nhân.
- Evidence hoặc cách tái hiện.
- Ảnh hưởng tới độ tin cậy.
- Biện pháp kiểm soát.
- Trạng thái đã kiểm chứng hoặc chưa kiểm chứng.

#### 4.4. Performance/risk experiment

Thực hiện kiểm chứng ở mức:

**80 người dùng/tác vụ đồng thời, p95 mục tiêu không quá 2.5 giây.**

Cần ghi:

- Công cụ/harness.
- Môi trường thực thi.
- Dữ liệu đầu vào hoặc fixtures.
- Số tác vụ đồng thời.
- Số lần chạy và cách đo.
- Latency measurements.
- p95 thực tế nếu đã chạy được.
- Error/failure count.
- Kết luận pass/fail so với mục tiêu.
- Giới hạn thí nghiệm.

Nếu không chạy được tải thật, phải trình bày harness, phương án giả lập và giới hạn kết luận đúng yêu cầu đề bài.

Không tự bịa p95 hoặc khẳng định hệ thống đạt hiệu năng mà không có log.

### PHẦN 5. ENGINEERING EVIDENCE VÀ REFLECTION

#### 5.1. Traceability

Tạo bảng:

**Acceptance Criterion/Risk → Test Case → Test File → Commit/PR → Result**

Các thành phần phải liên kết được với nhau.

Không dùng tên file hoặc commit giả.

Nếu test chưa chạy, ghi rõ trạng thái thay vì điền PASS.

#### 5.2. AI Usage Log

Bổ sung:

- Công cụ AI thực tế.
- Prompt chính.
- AI implementation plan.
- Assumptions ban đầu.
- Những chỉnh sửa/bác bỏ khi review plan.
- AI-generated patch.
- Post-test AI review.
- Nhận xét AI đúng.
- Nhận xét AI chưa đủ evidence.
- Những hạn chế của AI-generated code/tests.

#### 5.3. Hai điểm AI-generated code/tests chưa đáng tin

Chỉ ra ít nhất hai vấn đề thực sự xuất hiện trong output hoặc cần kiểm chứng thêm, ví dụ:

- Test chỉ kiểm tra HTTP status nhưng không xác minh data scope.
- Mock không phản ánh đúng database contract.
- AI giả định một permission rule không tồn tại.
- AI bỏ qua concurrent requests.
- AI tạo expected result dựa trên chính implementation.

Chỉ sử dụng các ví dụ này khi phù hợp với output/code thực tế.

#### 5.4. Reflection 250–350 từ

Viết reflection bằng tiếng Việt, khoảng 250–350 từ, có lập luận cá nhân.

Reflection cần trả lời:

1. Điều gì khiến confidence vào thay đổi tăng lên?
2. Test fail → patch → pass đã chứng minh điều gì?
3. Mutation experiment nói lên điều gì về sức mạnh của test suite?
4. Những gì vẫn chưa được chứng minh?
5. Test tiếp theo có giá trị cao nhất là gì và vì sao?

Reflection phải dựa trên evidence thực tế, không được tự tuyên bố đã thực hiện những công việc chưa xảy ra.
